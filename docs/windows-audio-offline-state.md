# Windows audio authorization across process restart

Status: versioned account storage, atomic audio-state persistence, finite membership checkpoint validation, owned registry/membership-query journaling and fresh playback-grant persistence are implemented; product offline restart recovery is not enabled. Credential-refresh journaling and the startup/UI admission path remain unimplemented. The native continuity and file-commit experiments establish only the specific boundaries listed below. A durable login identifier alone is not audio authority.

## Current product boundaries

`AccountSessionCoordinator.HydrateFromStoreCoreAsync` requires live account verification on launch. A temporary authentication failure retains the protected credentials but clears the published account identity. `AccountAudioAuthorization` and `AudioAccountMembershipProvider` are process-local. A valid cached membership can be reused within its original lifetime in that process; parsing saved JWT claims cannot substitute for previously verified audio authority after restart.

`SessionStore` now writes a schema-3 envelope in the existing `session.bin`: an explicit active/cleared state, a fresh mutation nonce, a durable login identifier for active state, the existing credential payload and optional audio state. Schema-1 credentials and schema-2 account envelopes remain readable without inventing audio authority. The revision exposed to callers identifies the complete protected bytes. Every save, clear or audio-state write must compare the captured revision while holding the permanent `.session.lock` file lease, then perform the write-through replacement. File contention fails explicitly; no retry, delete-first replacement or lease-file deletion is used. Reads and complete committed records are bounded to 1 MiB and close the record before replacement.

The internal `ISessionAudioStateStore` capability updates audio state in that same protected file. It requires the captured revision and durable login, copies credentials from the protected current head, and advances the common revision. A stale callback cannot overwrite a newer audio mutation, a completed clear or a replacement login, even if it learns the replacement revision. Continuing a login preserves its audio payload; a new login or clear discards it. The storage layer validates JSON framing, duplicate fields and capacity. It deliberately does not interpret that payload as authority: the audio layer must also validate its schema, exact bindings, deadlines, continuity and revocation state. The account coordinator now uses this capability for registry/membership-query preparation and completion, including a verified playback membership's original checkpoint. This does not enable offline startup.

An old owner can no longer restore a login after clear or erase a replacement login. Clearing an absent record also commits a tombstone, so a sign-in that captured absence before logout cannot commit afterward. Credential rotation and verified hydration preserve the durable login; an explicit new login receives a new identifier. Schema-1 credentials remain readable and can migrate on an accepted online refresh or verified account save. Reading them, or encountering a temporary network failure, does not issue an offline grant or extend a deadline. Unknown schemas and corrupt records remain distinguishable errors and are preserved at startup; an explicit clear requires the exact captured record revision.

`AccountSessionCoordinator` captures the revision before its network operation. A conflict retires that coordinator's in-memory/audio publication and does not delete or remotely sign out the replacement owner. Its user-facing sign-in error asks the user to reopen login after the account state changes. A read failure retains the prior owner revision; it cannot turn the next logout into an unconditional clear of whichever account is currently stored. The shared in-process mutation gate still serializes this coordinator's requests, but the file lease and revision also arbitrate separate processes. Existing `QPeriaptTrustedStateStore` policy state remains separate, with its own owner and format.

The shared `AtomicSessionFileCommitter` requests Windows write-through replacement after callers flush and close a same-directory temporary file. It preserves a native error as a failed commit. The account-store lease and revision checks supply ownership arbitration; atomic replacement alone does not.

A fresh-directory counterexample on the Mac host returned `SessionPersistenceFailed/IoFailure` at `AcquireLease`, HRESULT `0x80070002`, before the first synthetic verified login could commit. `File.GetAttributes` reported the absent final directory as `FileNotFoundException`, while the old loader recognized only `DirectoryNotFoundException` as absence. The loader now classifies absence only while inspecting the account directory; a non-directory, permission failure or later lease/read race retains its I/O error. The corrected first-login path and a non-directory counterexample pass. Windows-native validation of this change remains separate.

## Recovery contract

`AudioMembershipCheckpoint` captures an already verified runtime membership's evidence ID, account scope, exact device IDs/algorithms/fingerprints and original UTC/QPC issue/expiry anchors. Capture checks validity before and after creating the continuity tag. Restoration validates the schema, bounded finite interval, login/account/device bindings and current logon continuity, then samples the clock after verification. It constructs runtime evidence with the original ID and deadlines; it cannot use the fresh-grant constructor to renew them. Re-saving restored evidence preserves those same values. Capture now runs in the playback provider before its durable commit; restoration remains a component API, not a product startup admission path.

`WindowsAudioLogonContinuity` is the product implementation of the previously measured same-logon tag. The isolated native probe now links this implementation for positive creation and all recovery checks; its same-process creation code remains only to construct a negative test. The tag is a protected random nonce with a commitment authenticated by the enclosing account record. It is not standalone account authentication or storage encryption. [CryptUnprotectMemory](https://learn.microsoft.com/en-us/windows/win32/api/dpapi/nf-dpapi-cryptunprotectmemory) cannot preserve this continuity over an OS restart and may return unpredictable bytes when flags differ, so the commitment must match even after API success. Different logons and suspend/hibernate transitions remain separately unverified. This mechanism does not redefine the overall offline requirement as a same-logon-only feature.

The checkpoint component adds nine regression cases covering serialization under both protocol signing algorithms, original evidence/deadline preservation, changed login/account/tenant/device keys, malformed bounds and unknown fields, expiry/rollback, revocation during capture, expiry during logon verification, and observable protection failures. Seven storage cases cover unchanged credentials/login, preserved payload across rotation, stale callbacks after clear/relogin, common revision conflicts, malformed/oversized/duplicate input, schema-2 migration, invalid old/cleared envelopes, pre/post-commit failures and recovery after a separate writer exits. The host contract build has zero warnings/errors; all 125 focused account/audio cases and 35 storage cases pass. Host process tests use plaintext protection and a continuity fixture, not Windows cryptography.

The canonical protected account record now carries credentials, one durable login identifier, a mutation revision and an audio-state payload together. `AudioAccountJournalState` interprets that payload as bounded owned observations and finite checkpoints, never as an independently restorable grant file. `ReadRecoveryCandidates` rejects another login/scope and every nonempty pending set before exposing candidates; each candidate still requires the checkpoint's exact identity, expiry and logon validation. A fresh login creates a new login identifier; credential rotation and process restart retain the same identifier only when their identity continuity has been verified.

A restored membership must retain its original evidence ID, account authority/subject/tenant, both exact device protocol identities, issue time and both expiry anchors. The same-logon seal and the original UTC/QPC bounds must all be valid. Restoration cannot create a new duration, substitute a new connection identity or turn an expired record into a refresh. Source/output consent and the authenticated transport remain separate admission requirements.

The native experiment demonstrated a writer process exiting before another process reads its protected record in the same Windows logon. It did not exercise another real logon, OS restart, suspend, hibernation or physical playback. Those states remain separate gates; unsupported continuity must require a fresh verified grant.

## Mutation ordering to establish before enabling recovery

| Transition | Required ordering and failure result |
| --- | --- |
| Positive membership observation | Validate the captured account/login, request and device identities, commit the exact finite evidence, then publish recovery eligibility. A failed write cannot be reported as a saved grant. |
| Revocation-capable network operation | Establish a durable owned pending observation before sending the request. If preparation fails, do not send that operation. Implemented for registry presence/list/registration/removal; credentials and the playback provider's direct GET still need integration. |
| Known negative result | Revoke affected runtime consumers immediately. Atomically record the negative fact and retire only its owned pending observation. If completion cannot persist, the pending record must continue to deny restart recovery. |
| Temporary failure or cancellation | Settle the underlying operation before deciding whether its owned marker can be cleared. A canceled UI waiter cannot discard a completed negative response. No completed failure extends an existing grant. |
| Sign-out or account replacement | Commit an authoritative cleared/replaced record with a new revision. A late writer from the previous login must fail its revision/login check. A failed durable sign-out must remain visibly failed. |
| Corrupt, unknown or inaccessible record | Preserve the distinct failure. Do not fall back to an earlier credential file, an empty cache or a newly generated login identity. |

The pending-observation protocol addresses a specific gap: adding checkpoint serialization alone could allow restart to restore an old grant after a negative observation could not be saved. Compare-and-swap prevents stale owners from overwriting newer state; it does not by itself solve a failed invalidation write. Registry operations now implement this ordering. It is not yet a complete application-wide recovery protocol because the other revocation-capable call paths remain outside the journal.

`AccountDeviceRosterClient` now awaits `BeginAsync` before each individual presence, list, registration and removal request. A failed preparation sends no HTTP request. A successful preparation has exactly one awaited `CompleteAsync` after the underlying operation and its result callback settle, including transport failure, cancellation, malformed responses and observer failures. Completion receives the actual outcome and has no UI cancellation token. Parsed denials/removals still revoke runtime evidence before completion; failures in both the request and completion retain both causes. Enrollment recovery does not retire an outer marker belonging to multiple requests: each actual request has its own captured account and observation interval.

Eight lifecycle regressions cover preparation rejection for all four operations, enrollment recovery, cancellation during preparation and during an unsettled request, completion barriers, malformed/transport/unknown failures and combined notification/completion failures and local errors that mimic server enrollment replies. Their original host build has zero warnings/errors, and all 133 focused account/audio cases passed. Evidence is under `artifacts/audio-native-20261020/registry-observation-lifecycle-v1/`.

The registry observer now binds its journal store to the exact account publication. Preparation/completion share the account coordinator's mutation gate with credential writes and sign-out, and perform protected file I/O on a worker thread. Each request has one exact durable owner; completion removes only that entry. Verified negative snapshots and removals retire matching checkpoints; an uncertain removal retires its selected identity. Allowlisted temporary reads preserve the original finite evidence, while TLS/protocol/identity failures cannot act as a temporary fallback. No observation issues, renews or recreates a checkpoint. A verified change of protected account scope starts an empty journal without moving the old scope's evidence. A retired callback cannot write to a new publication; a failed durable completion leaves its pending entry or its already-committed negative result observable.

The registry-only revision `2a11ec03` added fourteen regressions exercising the real roster request path and canonical file with synthetic authentication/registry responses: preparation before HTTP, targeted revocation, temporary/uncertain results, pre/post-replacement failures, token/scope changes, interleaved owners, stale completions, external writers, malformed/unknown state, capacity, recovery denial while pending, non-issuance, cancellation during prepared replacement and worker-thread commits. Both contract-test and offline-recovery-probe projects built on the Mac host with zero warnings/errors; all 147 focused account/audio cases and 36 storage cases passed. Host files used a plaintext protection fixture and synthetic continuity seals. The tests select CurrentUser DPAPI on Windows. Evidence is under `artifacts/audio-native-20261020/owned-audio-journal-v1/`; Windows-native verification of this revision remains separate.

The playback provider now prepares an exact local/peer query owner before its read-only registry GET. A successful response may persist only its own finite evidence ID, account/device bindings and original clock anchors, and the canonical commit must succeed before a playback lease is published or continued. Cancellation, negative replies and failed sealing settle their exact pending request without issuing a grant. A failed or uncertain commit is reported and is never retried; post-replacement failure may leave a checkpoint on disk but cannot return a successful playback lease. Disk and logon sealing work run outside playback/cache locks and off the caller UI thread.

Journal schema 2 adds exact membership peers and sticky contradictions to pending owners. Confirmed removals and negative snapshots mark affected in-flight queries, so a later positive response cannot recreate their authority even when the two observations came through different provider instances. Schema-1 registry-only data preserves every original checkpoint and pending marker during migration and cannot acquire a fabricated membership owner. A peer denial or superseded query preserves unrelated finite evidence. A device-denial body remains terminal even under HTTP 503. Fresh authenticated observations can reclaim records already rejected by their original clock bounds; full capacity never silently evicts a still-valid record.

Fourteen additional membership-journal cases pass as part of 161 focused account/audio cases, with a warning-free Mac host build. They exercise actual query parsing and canonical-file writes, late/canceled responses, cross-provider revocation, explicit continuation, first/post-replacement faults, temporary versus terminal errors, logon-seal failures, account replacement, schema migration, binding substitution and capacity. The capacity case first reproduced an expired full store blocking a newly verified device; the corrected implementation passes that case and the still-valid full-store refusal. The error-classification regression and capacity counterexample logs remain under `artifacts/audio-native-20261020/membership-journal-v1/`. Host protection/continuity fixtures are not Windows cryptographic proof; the same journal fixture selects CurrentUser DPAPI and the product logon seal on Windows. The complete host suite passed 841 distinct cases. Subsequent schema-2 required-field validation and its malformed-record cases passed the final warning-free build and 161 focused cases; the receipt separates those two source snapshots. The FFI/static client gate also passed. Windows-native validation remains pending and must be checked against the exact source revision. Credential-refresh journaling and product startup recovery remain open.

Disk and network work must stay outside the playback effect gate. That gate remains a bounded in-memory check of the exact consumer, account epoch and finite evidence. Persistence needs its own bounded ownership protocol; acquiring it must not hold the carrier or output lock.

## Migration and native validation

The current migration preserves existing credentials while adding no audio authority to schema-1 data. The same canonical file is replaced atomically, so a tombstone cannot fall back to a separate older credential file. There is no downgrade conversion or supported coexistence with older executables that ignore the new lease/protocol. The evidence covers participating current-version writers; it does not establish protection against an older binary or a same-user process replacing/deleting stored files. That installation/version boundary must remain explicit before offline recovery is admitted.

A deterministic pre-change case reproduced stale credentials being saved after another store instance completed sign-out. A separate counterexample reproduced a read failure discarding the owner revision and allowing a later logout to clear a replacement; the corrected coordinator retains that revision. The revised storage and account tests also cover a pending first login overtaken by logout, stale clear, same-account relogin, preserved login identity across rotation/hydration, legacy migration, malformed/unknown/oversized records, failed clear commits, delayed network responses, two independent stale-writer/clearer processes and OS lease release after terminating its owner. Faults injected after actual record replacement check that an I/O failure is not treated as proof that no commit occurred: the operation remains failed and its old revision cannot overwrite the committed result.

The host build has zero warnings/errors; all 28 storage cases, 116 account/audio/LAN cases and 788 distinct full-suite cases pass. Host checks use synthetic account responses and a plaintext protection fixture; Windows runs use CurrentUser DPAPI for these filesystem/process cases. Their command logs, source hashes and both counterexamples are under `artifacts/audio-native-20261019/session-versioned-state-v1/`.

The earlier native file experiments exercised process-stop boundaries before and after the commit call, rejection with complete records retained while a target is open, and successful lease release in those specific runs. Both the old `File.Move` and the new write-through path reject an open replacement target in the measured Windows environment, even with `FileShare.Delete`. Readers must close before committing; there is no new delete-first or retry path. The [Windows rename contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) distinguishes standard replacement from POSIX semantics.

Required acceptance still includes:

- Repeat the verified two-process account races with persisted audio checkpoints, including an old asynchronous writer after sign-out and same-account relogin.
- Failure before request preparation, after a known negative, during replacement and during cleanup, with separate restart readback.
- Overlapping credential and registry observations, including canceled waiters and changed owners.
- Extend the verified account-record migration, cleared-state, corruption and protection boundaries to audio checkpoint state.
- Recovery of the original deadlines without renewal, plus expiry, clock rollback and logon mismatch rejection.
- Product startup, authenticated USB/Wi-Fi reconnection and actual strict audio output using restored evidence.

Power-loss durability and interruption inside the rename syscall were not tested. [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) documents the write-through request; successful process-interruption experiments are not a substitute for those stronger failure conditions.
