# Windows audio authorization across process restart

Status: versioned account storage is implemented; product offline restart recovery is not enabled. The native continuity and file-commit experiments establish only the specific boundaries listed below. A durable login identifier alone is not audio authority.

## Current product boundaries

`AccountSessionCoordinator.HydrateFromStoreCoreAsync` requires live account verification on launch. A temporary authentication failure retains the protected credentials but clears the published account identity. `AccountAudioAuthorization` and `AudioAccountMembershipProvider` are process-local. A valid cached membership can be reused within its original lifetime in that process; parsing saved JWT claims cannot substitute for previously verified audio authority after restart.

`SessionStore` now uses a schema-2 envelope in the existing `session.bin`: an explicit active/cleared state, a fresh mutation nonce, a durable login identifier for active state and the existing credential payload. It carries no audio checkpoint yet. The revision exposed to callers identifies the complete protected bytes. Every save or clear must compare the captured revision while holding the permanent `.session.lock` file lease, then perform the write-through replacement. File contention fails explicitly; no retry, delete-first replacement or lease-file deletion is used. Reads are bounded to 1 MiB and close the record before replacement.

An old owner can no longer restore a login after clear or erase a replacement login. Clearing an absent record also commits a tombstone, so a sign-in that captured absence before logout cannot commit afterward. Credential rotation and verified hydration preserve the durable login; an explicit new login receives a new identifier. Schema-1 credentials remain readable and can migrate on an accepted online refresh or verified account save. Reading them, or encountering a temporary network failure, does not issue an offline grant or extend a deadline. Unknown schemas and corrupt records remain distinguishable errors and are preserved at startup; an explicit clear requires the exact captured record revision.

`AccountSessionCoordinator` captures the revision before its network operation. A conflict retires that coordinator's in-memory/audio publication and does not delete or remotely sign out the replacement owner. Its user-facing sign-in error asks the user to reopen login after the account state changes. A read failure retains the prior owner revision; it cannot turn the next logout into an unconditional clear of whichever account is currently stored. The shared in-process mutation gate still serializes this coordinator's requests, but the file lease and revision also arbitrate separate processes. Existing `QPeriaptTrustedStateStore` policy state remains separate, with its own owner and format.

The shared `AtomicSessionFileCommitter` requests Windows write-through replacement after callers flush and close a same-directory temporary file. It preserves a native error as a failed commit. The account-store lease and revision checks supply ownership arbitration; atomic replacement alone does not.

## Recovery contract

A future canonical protected account record must bind credentials, one durable login identifier, a mutation revision and audio checkpoint state. These fields cannot be committed independently. A fresh login creates a new login identifier; credential rotation and process restart retain the same identifier only when their identity continuity has been verified.

A restored membership must retain its original evidence ID, account authority/subject/tenant, both exact device protocol identities, issue time and both expiry anchors. The same-logon seal and the original UTC/QPC bounds must all be valid. Restoration cannot create a new duration, substitute a new connection identity or turn an expired record into a refresh. Source/output consent and the authenticated transport remain separate admission requirements.

The native experiment demonstrated a writer process exiting before another process reads its protected record in the same Windows logon. It did not exercise another real logon, OS restart, suspend, hibernation or physical playback. Those states remain separate gates; unsupported continuity must require a fresh verified grant.

## Mutation ordering to establish before enabling recovery

| Transition | Required ordering and failure result |
| --- | --- |
| Positive membership observation | Validate the captured account/login, request and device identities, commit the exact finite evidence, then publish recovery eligibility. A failed write cannot be reported as a saved grant. |
| Revocation-capable network operation | Establish a durable owned pending observation before sending the request. If preparation fails, do not send that operation. This candidate protocol still needs implementation and fault tests. |
| Known negative result | Revoke affected runtime consumers immediately. Atomically record the negative fact and retire only its owned pending observation. If completion cannot persist, the pending record must continue to deny restart recovery. |
| Temporary failure or cancellation | Settle the underlying operation before deciding whether its owned marker can be cleared. A canceled UI waiter cannot discard a completed negative response. No completed failure extends an existing grant. |
| Sign-out or account replacement | Commit an authoritative cleared/replaced record with a new revision. A late writer from the previous login must fail its revision/login check. A failed durable sign-out must remain visibly failed. |
| Corrupt, unknown or inaccessible record | Preserve the distinct failure. Do not fall back to an earlier credential file, an empty cache or a newly generated login identity. |

The pending-observation protocol addresses a specific gap: adding checkpoint serialization alone could allow restart to restore an old grant after a negative observation could not be saved. Compare-and-swap prevents stale owners from overwriting newer state; it does not by itself solve a failed invalidation write. This protocol is a candidate design, not a claim that the current application already provides the property.

`AudioAccountRegistryObserver` currently has `Begin`, `Listed`, `Removed` and `Rejected` callbacks. Durable integration must also settle every operation that exits with a transport failure or cancellation. This affects presence, list, registration, removal and credential-refresh call paths, not only the playback provider's direct GET. Completion must retain captured ownership and must not follow the currently displayed account to a replacement login.

Disk and network work must stay outside the playback effect gate. That gate remains a bounded in-memory check of the exact consumer, account epoch and finite evidence. Persistence needs its own bounded ownership protocol; acquiring it must not hold the carrier or output lock.

## Migration and native validation

The current migration preserves existing credentials while adding no audio authority to schema-1 data. The same canonical file is replaced atomically, so a tombstone cannot fall back to a separate older credential file. There is no downgrade conversion or supported coexistence with older executables that ignore the new lease/protocol. The evidence covers participating current-version writers; it does not establish protection against an older binary or a same-user process replacing/deleting stored files. That installation/version boundary must remain explicit before offline recovery is admitted.

A deterministic pre-change case reproduced stale credentials being saved after another store instance completed sign-out. A separate counterexample reproduced a read failure discarding the owner revision and allowing a later logout to clear a replacement; the corrected coordinator retains that revision. The revised storage and account tests also cover a pending first login overtaken by logout, stale clear, same-account relogin, preserved login identity across rotation/hydration, legacy migration, malformed/unknown/oversized records, failed clear commits, delayed network responses, two independent stale-writer/clearer processes and OS lease release after terminating its owner. Faults injected after actual record replacement check that an I/O failure is not treated as proof that no commit occurred: the operation remains failed and its old revision cannot overwrite the committed result.

The host build has zero warnings/errors; all 28 storage cases, 116 account/audio/LAN cases and 788 distinct full-suite cases pass. Host checks use synthetic account responses and a plaintext protection fixture; Windows runs use CurrentUser DPAPI for these filesystem/process cases. Their command logs, source hashes and both counterexamples are under `artifacts/audio-native-20261019/session-versioned-state-v1/`.

Native run [39316954920](https://github.com/billlza/Skybridge-Compass-Windows/actions/runs/39316954920), at commit `48207b399d0193f52375d123312a408b1c94f87e`, passed both builds with zero warnings/errors and 110 distinct cases before failure. The isolated `AudioOfflineRecoveryProbe --lease-study` links the actual product `SessionStore` and compares orderly release with forced process termination. It preserves the first save result and stops after the first failure, without retrying the mutation. Bounded subsequent opens observe availability only. It also calibrates a Restart Manager query against a known live holder, then queries the same synthetic file on failure. [Restart Manager lists applications and services using registered resources](https://learn.microsoft.com/en-us/windows/win32/api/restartmanager/nf-restartmanager-rmgetlist); an empty result is not proof that every kernel handle has disappeared. Registration performs internal bookkeeping, but this experiment never calls shutdown/restart or changes access controls. Query latency is included in the recorded elapsed observation times. This experiment is pending native execution and does not change the product lease policy.

The earlier native file experiments exercised process-stop boundaries before and after the commit call, rejection with complete records retained while a target is open, and successful lease release in those specific runs. The later sharing-violation counterexamples above keep immediate post-termination availability unresolved. Both the old `File.Move` and the new write-through path reject an open replacement target in the measured Windows environment, even with `FileShare.Delete`. Readers must close before committing; there is no new delete-first or retry path. The [Windows rename contract](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/ntifs/ns-ntifs-_file_rename_information) distinguishes standard replacement from POSIX semantics.

Required acceptance still includes:

- Real two-process stale-write races, including an old asynchronous writer after sign-out and same-account relogin.
- Failure before request preparation, after a known negative, during replacement and during cleanup, with separate restart readback.
- Overlapping credential and registry observations, including canceled waiters and changed owners.
- Legacy migration, authoritative cleared-state precedence, corruption and unavailable protection.
- Recovery of the original deadlines without renewal, plus expiry, clock rollback and logon mismatch rejection.
- Product startup, authenticated USB/Wi-Fi reconnection and actual strict audio output using restored evidence.

Power-loss durability and interruption inside the rename syscall were not tested. [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw) documents the write-through request; successful process-interruption experiments are not a substitute for those stronger failure conditions. Detailed native receipts are tracked in [the output qualification record](windows-audio-native-output.md).
